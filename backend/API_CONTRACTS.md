# RoamNest API Contracts

## 1. Загальна інформація

**Base URL:** `http://127.0.0.1:8000`


**Джерело даних:** Backend використовує Django ORM та PostgreSQL для роботи з користувачами, 
профілями, об'єктами житла (`Property`), типами розміщення (`RentalUnit`), бронюваннями (`Booking`), 
зручностями, категоріями, добірками та зображеннями.

**Доступ та автентифікація:** Операції з бронюваннями використовують реальну базу даних PostgreSQL. 
Створення бронювань, перевірка доступності, зміна статусів та скасування виконуються через Django ORM. 
Для захисту від одночасного бронювання використовується транзакційне блокування `select_for_update()`.

У прикладах `{id}` означає числовий ID ресурсу.

## 3. Authentication — автентифікація

Система підтримує реєстрацію та авторизацію користувачів із двома ролями:

- `USER` — гість;
- `OWNER` — власник житла.

Публічна реєстрація доступна тільки для ролей `USER` та `OWNER`.
Роль `ADMIN` призначається адміністратором через адміністративний API.

### 3.1. POST `/api/auth/register/` — реєстрація

**Доступ:** публічний, авторизація не потрібна.

Створює нового користувача та пов'язаний із ним профіль у PostgreSQL.

**Обов'язкові поля запиту:**

| Поле | Тип | Опис |
|---|---|---|
| `first_name` | string | Ім'я користувача |
| `last_name` | string | Прізвище користувача |
| `email` | string | Електронна пошта |
| `password` | string | Пароль, мінімум 8 символів |
| `password_confirm` | string | Підтвердження пароля |
| `role` | string | Роль: `USER` або `OWNER` |

**Необов'язкове поле:**

| Поле | Тип | Опис |
|---|---|---|
| `username` | string | Ім'я користувача в системі. Якщо не передане, генерується автоматично на основі email |

**Приклад реєстрації гостя:**

```json
{
  "first_name": "Олена",
  "last_name": "Бенедюк",
  "email": "guest@example.com",
  "password": "ExamplePass123!",
  "password_confirm": "ExamplePass123!",
  "role": "USER"
}
```

**Приклад реєстрації власника:**

```json
{
  "first_name": "Андрій",
  "last_name": "Петренко",
  "email": "owner@example.com",
  "password": "ExamplePass123!",
  "password_confirm": "ExamplePass123!",
  "role": "OWNER"
}
```

**Перевірки:**

- ім'я та прізвище обов'язкові;
- email повинен мати коректний формат;
- email повинен бути унікальним;
- пароль повинен відповідати мінімальній довжині та налаштованим вимогам Django;
- пароль і підтвердження пароля повинні збігатися;
- роль повинна бути `USER` або `OWNER`.

**Відповіді:**

- `201 Created` — користувача успішно зареєстровано;
- `400 Bad Request` — помилки валідації, зайнятий email або невідповідність паролів.

Реєстрація не повертає JWT. Для отримання токенів користувач повинен виконати авторизацію.

### 3.2. POST `/api/auth/login/` — авторизація

**Доступ:** публічний, авторизація не потрібна.

Виконує вхід користувача за електронною поштою та паролем.

**Поля запиту:**

| Поле | Тип | Опис |
|---|---|---|
| `email` | string | Електронна пошта |
| `password` | string | Пароль |

**Приклад запиту:**

```json
{
  "email": "guest@example.com",
  "password": "ExamplePass123!"
}
```

**Приклад успішної відповіді (`200 OK`):**

```json
{
  "access": "<access_token>",
  "refresh": "<refresh_token>",
  "user": {
    "id": 15,
    "username": "guest",
    "first_name": "Олена",
    "last_name": "Бенедюк",
    "email": "guest@example.com",
    "role": "USER"
  }
}
```

Для власника в полі `role` повертається `OWNER`.

**Відповіді:**

- `200 OK` — успішна авторизація;
- `400 Bad Request` — email або пароль не передані;
- `401 Unauthorized` — неправильні облікові дані або користувач неактивний.

### 3.3. POST `/api/auth/refresh/` — оновлення access-токена

**Доступ:** тільки авторизованому користувачу.

Повертає інформацію про користувача за його JWT access-токеном.

### 3.7. PATCH `/api/profile/` — редагування профілю

**Доступ:** тільки авторизованому користувачу.

**Дозволені поля:**

| Поле | Тип | Опис |
|---|---|---|
| `first_name` | string | Ім'я |
| `last_name` | string | Прізвище |
| `phone` | string | Номер телефону |
| `avatar` | string | URL аватара |

Зміна email через цей endpoint не дозволена.

**Відповіді:**

- `200 OK` — профіль успішно оновлено;
- `400 Bad Request` — некоректні дані або спроба змінити email;
- `401 Unauthorized` — користувач не авторизований.

### 3.8. Загальні правила автентифікації

Захищені endpoint-и потребують заголовка:

`Authorization: Bearer <access_token>`

Після авторизації backend повертає роль користувача (`USER`, `OWNER` або `ADMIN`), за якою визначаються доступні функції системи.

Типові відповіді:

- `401 Unauthorized` — відсутній або недійсний access-токен;
- `403 Forbidden` — користувач не має необхідних прав.

## 4. Properties --- житло

### 4.1. GET `/api/properties/`

Повертає список житла зі статусом `PUBLISHED`. Перед поверненням із
кожного об'єкта прибираються неопубліковані типи розміщення (`rental_units`).

#### Query-параметри

  ----------------------------------------------------------------------------
  Параметр                Тип                     Опис
  ----------------------- ----------------------- ----------------------------
  `city`                  string                  Пошук за входженням підрядка
                                                  в назву міста, без
                                                  урахування регістру

  `country`               string                  Пошук за входженням підрядка
                                                  в назву країни, без
                                                  урахування регістру

  `property_type`         string                  Точне порівняння типу житла
                                                  без урахування регістру

  `guests`                integer                 Залишає об'єкти, де є
                                                  опублікований тип розміщення
                                                  з `max_guests >= guests`

  `max_guests`            integer                 Залишає об'єкти, де є
                                                  опублікований тип розміщення
                                                  з `max_guests <= max_guests`

  `min_price`             number                  Мінімальна ціна за ніч,
                                                  включно з межею

  `max_price`             number                  Максимальна ціна за ніч,
                                                  включно з межею

  `amenities`             повторюваний integer    ID зручностей; об'єкт має
                                                  містити всі передані ID

  `category`              string                  Фільтрація за унікальним slug
                                                  активної категорії

  `ordering`              string                  `price` --- за зростанням
                                                  мінімальної ціни типу
                                                  розміщення; `-price` --- за
                                                  спаданням

  `check_in`	          string YYYY-MM-DD	      Дата заїзду. Передається разом із check_out.

  `check_out`             string YYYY-MM-DD	      Дата виїзду. Має бути пізніше за check_in.
  ----------------------------------------------------------------------------

   #### Пошук за датами

Параметри `check_in` та `check_out` використовуються
для пошуку доступного житла на обраний період.

Обидва параметри є необов'язковими, але якщо передається
один із них, другий також є обов'язковим.

Під час пошуку враховуються активні бронювання зі статусами
`PENDING` та `CONFIRMED`.

Правила перевірки доступності:

| Тип житла | Правило |
|---|---|
| `HOTEL` | Кількість активних бронювань менша за `rooms_count`. |
| `HOSTEL` | Сума гостей у бронюваннях разом із кількістю гостей запиту не перевищує `rooms_count`. |
| `APARTMENT` | Відсутні активні бронювання на обраний період. |
| `HOUSE` | Відсутні активні бронювання на обраний період. |
| `ROOM` | Відсутні активні бронювання на обраний період. |
| `VILLA` | Відсутні активні бронювання на обраний період. |

День виїзду одного бронювання може бути днем заїзду іншого.

Приклад:

`/api/properties/?check_in=2027-02-10&check_out=2027-02-12&guests=2`

Можна поєднувати дати з іншими фільтрами:
містом, країною, типом житла, кількістю гостей,
ціною, зручностями та сортуванням.

#### Помилки валідації дат

- `400 Bad Request` — передано тільки одну дату.
- `400 Bad Request` — некоректний формат або неіснуюча дата.
- `400 Bad Request` — дата заїзду в минулому.
- `400 Bad Request` — дата виїзду не пізніше дати заїзду.


Приклад:
`/api/properties/?city=Kyiv&guests=2&min_price=500&max_price=3000&amenities=1&amenities=2&ordering=price`
`/api/properties/?category=beach`
`/api/properties/?category=mountains`
`/api/properties/?category=nature&city=Яремче`

#### Відповіді

-   `200 OK` --- масив об'єктів.
-   `400 Bad Request`:
    -   `{"detail": "Invalid numeric filter parameter."}` --- некоректне
        числове значення, кількість гостей менша за 1 або від'ємна ціна;
    -   `{"detail": "min_price cannot exceed max_price."}` ---
        мінімальна ціна більша за максимальну;
    -   `{"detail": "amenities must contain integer IDs."}` --- ID
        зручності не є цілим числом;
    -   `{"detail": "Unsupported ordering parameter."}` ---
        непідтримуване значення `ordering`.

**Примітка:** сортування використовує мінімальну ціну серед
опублікованих типів розміщення. Якщо об'єкт не має жодного
опублікованого типу розміщення, сортування може спричинити помилку
сервера.

### 4.2. POST `/api/properties/`

Створює новий об'єкт житла зі статусом `NEW`.
Якщо `amenities` та `categories` не передані,
об'єкт створюється без зручностей і категорій.

#### Обов'язкові поля

  Поле              Тип
  ----------------- --------
  `title`           string
  `description`     string
  `property_type`   string
  `address`         string
  `city`            string
  `country`         string

Власник об'єкта визначається автоматично за поточним автентифікованим користувачем.
Передавати owner у тілі запиту не потрібно.

#### Відповіді

-   `201 Created` --- створений об'єкт.
-   `400 Bad Request`:
    -   `{"detail": "Required fields are missing.", "fields": [...]}`
        --- відсутні або порожні обов'язкові поля;

#### Необов'язкові поля

| Поле         | Тип               | Опис                  |
|--------------|-------------------|-----------------------|
| `amenities`  | array of integers | ID зручностей         |
| `categories` | array of integers | ID активних категорій |

Приклад:

```json
{
  "categories": [3, 4]
}
```

Передані категорії призначаються створеному об'єкту.
Якщо поле не передано, об'єкт створюється без категорій.

### 4.3. GET `/api/properties/{id}/`

Повертає деталі об'єкта лише тоді, коли його статус --- `PUBLISHED`.
Неопубліковані типи розміщення не включаються до `rental_units`.

-   `200 OK` --- об'єкт житла. Відповідь також містить масив categories
з інформацією про категорії об'єкта.
-   `404 Not Found` --- `{"detail": "Property not found."}`, якщо об'єкт
    відсутній або не опублікований.

### 4.4. PATCH `/api/properties/{id}/`

Дозволені поля:

-   `title`
-   `description`
-   `property_type`
-   `address`
-   `city`
-   `country`
-   `amenities`
-   `categories`

Оновлення виконується частково. Поля, які не передані в запиті, залишаються без змін.

Для текстових полів передаються непорожні рядки.

```json
{
    "categories": [3, 4, 5]
}
```

Для `amenities` та `categories` передаються масиви ID відповідних записів.

Якщо передано `categories` або `amenities`, попередній набір відповідних записів замінюється новим набором.

Інші поля не змінюються.

-   `200 OK` --- оновлений об'єкт.
-   `400 Bad Request` ---
    `{"detail": "<field> must be a non-empty string."}`, якщо передане
    дозволене поле не є непорожнім рядком.
-   `404 Not Found` --- `{"detail": "Property not found."}`.

### 4.5. DELETE `/api/properties/{id}/`

Змінює статус об'єкта на `INACTIVE`; об'єкт не видаляється зі списку.

-   `200 OK`:

    ``` json
    {
      "detail": "Property deactivated successfully.",
      "id": 1,
      "status": "INACTIVE"
    }
    ```

-   `404 Not Found` --- `{"detail": "Property not found."}`.

### 4.6.1. GET `/api/categories/`

Повертає список усіх активних категорій із таблиці `Category`.

**Доступ:** публічний, авторизація не потрібна.

Категорії сортуються за `sort_order`, а потім за `name`.

**Поля відповіді:**

| Поле | Тип | Опис |
|---|---|---|
| `id` | integer | ID категорії |
| `name` | string | Назва категорії |
| `slug` | string | Унікальний код категорії |
| `description` | string | Опис |
| `image_url` | string | URL зображення |
| `sort_order` | integer | Порядок відображення |

**Відповідь:** `200 OK` — масив активних категорій. Якщо активних категорій немає, повертається `[]`.

### 4.6.2. Фільтрація за категорією

**GET** `/api/properties/?category={slug}`

Повертає опубліковані об'єкти нерухомості, які належать до вказаної активної категорії.

Один об'єкт може належати до декількох категорій.

Приклади доступних slug:

| Назва | slug |
|---|---|
| Пляж | `beach` |
| Місто | `city` |
| Природа | `nature` |
| Гори | `mountains` |
| Романтичний відпочинок | `romantic` |

Параметр `category` можна комбінувати з іншими фільтрами каталогу.

**Відповіді:**
- `200 OK` — масив відповідних об'єктів.
- `200 OK` з порожнім масивом `[]` — якщо відповідних об'єктів немає.

### 4.7. Property Collections — добірки житла

#### 4.7.1. GET `/api/collections/`

Повертає список активних добірок із таблиці `PropertyCollection`.

**Доступ:** публічний, авторизація не потрібна.

Повертаються тільки:
- активні добірки (`is_active = true`);
- опубліковані об'єкти нерухомості (`status = PUBLISHED`);
- опубліковані типи розміщення (`is_published = true`).

Добірки сортуються за `sort_order`, потім за `name`.

**Поля добірки:**

| Поле | Тип | Опис |
|---|---|---|
| `id` | integer | ID добірки |
| `name` | string | Назва |
| `slug` | string | Унікальний код |
| `description` | string | Опис |
| `image_url` | string | URL зображення |
| `sort_order` | integer | Порядок відображення |
| `properties` | array | Масив об'єктів нерухомості |

Кожен об'єкт у `properties` містить дані `PropertyListSerializer`:
інформацію про житло, зручності, категорії, опубліковані
типи розміщення та зображення.

**Приклади доступних добірок:**

| Назва | slug |
|---|---|
| Популярні | `popular` |
| Довгострокова оренда | `long-term` |
| Раннє бронювання | `early-booking` |

**Відповіді:**
- `200 OK` — масив активних добірок.
- `200 OK` з порожнім масивом `[]` — якщо активних добірок немає.

**Примітка:** склад добірок формується адміністратором вручну.
Автоматичний розрахунок популярності, тривалості проживання
або умов раннього бронювання наразі не реалізований.

### 4.8. Rental Units — типи розміщення (кімнати)

API забезпечує перегляд, створення, редагування та
деактивацію типів розміщення, пов'язаних з об'єктами житла.

На відміну від частини endpoint-ів Properties, операції з
RentalUnit використовують Django ORM та реальну базу даних.

#### 4.8.1. GET `/api/properties/{id}/rooms/`

Повертає список опублікованих кімнат конкретного об'єкта житла.

**Доступ:** Guest, USER, OWNER, ADMIN.

- `200 OK` — масив опублікованих кімнат.
- `404 Not Found` — об'єкт житла відсутній або не опублікований.

#### 4.8.2. POST `/api/properties/{id}/rooms/`

Створює новий тип розміщення для зазначеного об'єкта житла.

**Доступ:** лише автентифікований користувач
із роллю `OWNER`, якому належить об'єкт.

**Поля запиту:**

| Поле | Тип | Опис |
|---|---|---|
| `title` | string | Назва кімнати |
| `description` | string | Опис |
| `room_type` | string | Тип розміщення |
| `price_per_night` | decimal | Ціна за ніч |
| `max_guests` | integer | Максимальна кількість гостей |
| `bedrooms` | integer | Кількість спалень |
| `beds` | integer | Кількість ліжок |
| `bathrooms` | integer | Кількість ванних кімнат |
| `rooms_count` | integer | Кількість доступних кімнат |
| `amenities` | array of integers | ID зручностей |
| `is_published` | boolean | Статус публікації |

**Відповіді:**

- `201 Created` — кімнату створено.
- `400 Bad Request` — некоректні або невалідні дані.
- `401 Unauthorized` — відсутній або недійсний токен.
- `403 Forbidden` — користувач не має ролі OWNER або не володіє об'єктом.
- `404 Not Found` — об'єкт житла не знайдений.

#### 4.8.3. GET `/api/properties/rooms/{id}/`

Повертає детальну інформацію про опубліковану кімнату.

**Доступ:** Guest, USER, OWNER, ADMIN.

- `200 OK` — інформація про кімнату.
- `404 Not Found` — кімната відсутня, не опублікована
або її об'єкт житла не опублікований.

#### 4.8.4. PATCH `/api/properties/rooms/{id}/`

Оновлює дані кімнати.

**Доступ:** лише автентифікований власник (`OWNER`), якому належить об'єкт житла.

Дозволяється часткове оновлення полів кімнати.

- `200 OK` — оновлена інформація про кімнату.
- `400 Bad Request` — невалідні дані.
- `401 Unauthorized` — відсутній або недійсний токен.
- `403 Forbidden` — користувач не має ролі OWNER або
намагається змінити кімнату іншого власника.
- `404 Not Found` — кімната не знайдена.

#### 4.8.5. DELETE `/api/properties/rooms/{id}/`

Деактивує кімнату шляхом встановлення `is_published = false`.

Фізичне видалення запису з бази даних не виконується.

**Доступ:** лише автентифікований власник (`OWNER`), якому належить об'єкт житла.

**Відповіді:**

- `200 OK` — успішна деактивація:

```json
{
  "detail": "Room deactivated successfully.",
  "id": 4,
  "is_published": false
}
```

- `401 Unauthorized` — відсутній або недійсний токен.
- `403 Forbidden` — недостатньо прав доступу.
- `404 Not Found` — кімната не знайдена.

Після деактивації кімната не повертається в публічному списку
та недоступна через публічний endpoint отримання деталей.

#### Перевірка прав доступу

Під час тестування перевірено такі сценарії:

| Сценарій | HTTP-статус |
|---|---:|
| OWNER створює кімнату | 201 |
| OWNER переглядає кімнату | 200 |
| OWNER редагує власну кімнату | 200 |
| OWNER деактивує власну кімнату | 200 |
| Guest переглядає опубліковані кімнати | 200 |
| Guest отримує деактивовану кімнату | 404 |
| USER намагається створити кімнату | 403 |
| USER намагається редагувати кімнату | 403 |
| USER намагається деактивувати кімнату | 403 |
| OWNER намагається редагувати чужу кімнату | 403 |

Таким чином, перевірено базові CRUD-операції, автентифікацію,
рольовий доступ та контроль належності кімнати власнику об'єкта.

## 5. Property Images — зображення житла

Фотографії житла зберігаються в таблиці `PropertyImage`.

Фізичні файли зберігаються в об'єктному сховищі Supabase Storage через S3-compatible API. Backend працює зі сховищем через `boto3`. У базі даних зберігаються публічна URL-адреса фотографії (`image_url`) та ключ об'єкта (`image_key`).

Frontend отримує `image_url` через API і використовує його для відображення фотографій. Frontend не працює безпосередньо з S3-ключами та секретними параметрами сховища.

### 5.1. Загальні правила

Фотографії можуть належати:

- безпосередньо об'єкту `Property`, якщо `rental_unit` не передано;
- конкретному типу розміщення `RentalUnit`, якщо передано його ID.

Для кожної групи фотографій ведеться окремий облік головного зображення (`is_main`).

**Права доступу:**

- користувач повинен бути авторизований через JWT;
- додавати та видаляти фотографії може тільки користувач із роллю `OWNER`;
- власник може керувати фотографіями тільки власного об'єкта;
- переданий `rental_unit` повинен належати відповідному `Property`.

**Обмеження файлів:**

| Параметр | Значення |
|---|---|
| Дозволені формати | JPEG, PNG, WEBP |
| Максимальний розмір | 10 MB |
| Передача файлу | `multipart/form-data` |

Формат файлу перевіряється за сигнатурою, а не лише за розширенням або MIME-типом.

### 5.2. POST `/api/properties/{id}/images/`

Завантаження фотографії житла або окремого типу розміщення.

**Authorization:**

`Bearer <access_token>`

**Content-Type:**

`multipart/form-data`

**Поля запиту:**

| Поле | Тип | Обов'язкове | Опис |
|---|---|---|---|
| `image` | File | Так | Файл фотографії |
| `is_main` | boolean | Ні | Чи зробити фотографію головною. За замовчуванням `false` |
| `rental_unit` | integer | Ні | ID типу розміщення (`RentalUnit`). Якщо відсутній — фотографія належить безпосередньо житлу |

Для завантаження фотографії всього житла поле `rental_unit` не передається.

**Приклад запиту для Property:**

```text
POST /api/properties/1/images/
```

Body — `multipart/form-data`:

```text
image: apartment.jpg
is_main: true
```

**Приклад запиту для RentalUnit:**

```text
POST /api/properties/1/images/
```

Body — `multipart/form-data`:

```text
image: bedroom.jpg
is_main: false
rental_unit: 1
```

**Правила призначення головного зображення:**

- перша фотографія у відповідній групі автоматично стає головною, навіть якщо передано `is_main=false`;
- якщо передано `is_main=true`, попереднє головне фото цієї групи перестає бути головним;
- фотографії `Property` та `RentalUnit` мають незалежні групи головних зображень.

**Зберігання файлу:**

Backend генерує унікальний ключ об'єкта:

Для фотографії житла:

```text
properties/{property_id}/{uuid}.{extension}
```

Для фотографії типу розміщення:

```text
properties/{property_id}/units/{rental_unit_id}/{uuid}.{extension}
```

Файл завантажується в Storage. Після успішного завантаження створюється запис у таблиці `PropertyImage`.

**Приклад успішної відповіді:**

`201 Created`

```json
{
  "id": 15,
  "image_url": "https://storage.example.com/roamnest-images/properties/1/example.jpg",
  "is_main": true,
  "rental_unit": null
}
```

У відповіді `image_url` містить фактичну публічну адресу сховища. `image_key` зберігається в базі даних, але не повертається цим серіалізатором.

**Можливі відповіді:**

| HTTP Status | Опис |
|---|---|
| `201 Created` | Фотографію успішно завантажено |
| `400 Bad Request` | Не передано файл, неправильний формат, розмір понад 10 MB або `RentalUnit` не належить цьому житлу |
| `401 Unauthorized` | Відсутній або недійсний JWT |
| `403 Forbidden` | Користувач не має ролі OWNER або намагається керувати чужим житлом |
| `404 Not Found` | Житло не знайдено |
| `502 Bad Gateway` | Не вдалося завантажити файл у Storage |

Приклади помилок валідації:

```json
{
  "image": [
    "Only JPEG, PNG and WEBP images are supported."
  ]
}
```

```json
{
  "image": [
    "Image size must not exceed 10 MB."
  ]
}
```

```json
{
  "rental_unit": [
    "Rental unit not found for this property."
  ]
}
```

### 5.3. DELETE `/api/properties/{id}/images/{image_id}/`

Видалення фотографії з об'єкта житла.

**Authorization:**

`Bearer <access_token>`

Body не потрібен.

**Логіка роботи:**

1. Backend перевіряє авторизацію, роль OWNER та належність житла користувачу.
2. Знаходить фотографію за `image_id` та `property_id`.
3. Видаляє запис із бази даних.
4. Видаляє фізичний файл зі Storage за `image_key`.
5. Якщо видалене зображення було головним, наступна фотографія цієї групи автоматично стає головною.

**Успішна відповідь:**

`204 No Content`

Тіло відповіді відсутнє.

**Можливі відповіді:**

| HTTP Status | Опис |
|---|---|
| `204 No Content` | Запис і файл успішно видалені |
| `401 Unauthorized` | Відсутній або недійсний JWT |
| `403 Forbidden` | Недостатньо прав або житло не належить користувачу |
| `404 Not Found` | Житло або фотографію не знайдено |
| `502 Bad Gateway` | Запис видалено з бази, але не вдалося видалити фізичний файл зі Storage |

У разі помилки видалення файла Backend записує помилку в журнал.

### 5.4. Отримання фотографій через Property API

Фотографії повертаються в межах відповідей:

- `GET /api/properties/`
- `GET /api/properties/{id}/`

Фотографії самого житла повертаються в масиві `images`.

Фотографії кожного `RentalUnit` повертаються окремо в масиві `rental_units[].images`.

**Приклад відповіді:**

```json
{
  "id": 1,
  "title": "Cozy Apartment",
  "images": [
    {
      "id": 8,
      "image_url": "https://storage.example.com/property-main.jpg",
      "is_main": true,
      "rental_unit": null
    }
  ],
  "rental_units": [
    {
      "id": 1,
      "title": "Основний варіант",
      "images": [
        {
          "id": 9,
          "image_url": "https://storage.example.com/room-main.jpg",
          "is_main": true,
          "rental_unit": 1
        }
      ]
    }
  ]
}
```

Фотографії `RentalUnit` не дублюються в масиві `Property.images`.

Для відображення фотографій Frontend використовує поле `image_url`.

## 7. Bookings --- бронювання

Управління бронюваннями реалізоване через Django ORM та базу даних PostgreSQL.

Для бронювання використовується модель `Booking`, пов'язана з користувачем (`User`) та типом розміщення (`RentalUnit`).

### 7.1. GET `/api/bookings/`

Повертає список бронювань поточного автентифікованого користувача.

**Доступ:** будь-який авторизований користувач.
Повертаються тільки його власні бронювання.

Користувач визначається автоматично через JWT (`request.user`).

- `200 OK` — масив бронювань користувача.
- `401 Unauthorized` — відсутній або недійсний токен.

### 7.2. POST `/api/bookings/`

Створює нове бронювання.

**Доступ:** тільки авторизований користувач із роллю `USER`.

#### Обов'язкові поля

| Поле | Тип | Опис |
|---|---|---|
| `rental_unit` | integer | ID типу розміщення |
| `check_in` | string `YYYY-MM-DD` | Дата заїзду |
| `check_out` | string `YYYY-MM-DD` | Дата виїзду |
| `guests` | integer | Кількість гостей |
| `contact_name` | string | Ім'я контактної особи |
| `contact_phone` | string | Телефон |
| `contact_email` | string | Email |

**Необов'язкове поле:**

| Поле | Тип | Опис |
|---|---|---|
| `special_requests` | string | Додаткові побажання |

Користувач визначається автоматично за JWT. Передавати `user` у тілі запиту не потрібно.

#### Приклад запиту

```json
{
    "rental_unit": 15,
    "check_in": "2026-12-10",
    "check_out": "2026-12-15",
    "guests": 1,
    "contact_name": "Test User",
    "contact_phone": "+380991112233",
    "contact_email": "test@example.com",
    "special_requests": "Late check-in"
}
```

#### Перевірки

- Дата заїзду не може бути в минулому.
- Дата виїзду повинна бути пізніше за дату заїзду.
- Кількість гостей повинна бути не меншою за 1.
- Для HOTEL, APARTMENT, HOUSE, ROOM та VILLA
  кількість гостей не повинна перевищувати `max_guests`.
- Для HOSTEL кількість гостей в одному бронюванні
  може перевищувати `max_guests`, але сумарна кількість
  гостей в активних бронюваннях не повинна перевищувати
  `rooms_count` (кількість ліжок).
- Тип розміщення повинен бути опублікований (`is_published = true`).
- Об'єкт житла повинен мати статус `PUBLISHED`.
- Перевіряється перетин дат з іншими бронюваннями.
- Активними вважаються бронювання зі статусами `PENDING` та `CONFIRMED`.

#### Правила доступності

| Тип житла | Правило |
|---|---|
| `HOTEL` | Кількість одночасних активних бронювань не повинна перевищувати `rooms_count` |
| `HOSTEL` | Сумарна кількість гостей в активних бронюваннях не повинна перевищувати `rooms_count` (кількість ліжок) |
| `APARTMENT` | Одне бронювання на період |
| `HOUSE` | Одне бронювання на період |
| `ROOM` | Одне бронювання на період |
| `VILLA` | Одне бронювання на період |

Під час перевірки доступності враховуються бронювання зі статусами `PENDING` та `CONFIRMED`.

Бронювання зі статусами `CANCELLED`, `REJECTED`, `COMPLETED` та `NO_SHOW` не займають доступність.

Дати бронювання перевіряються за правилом перетину інтервалів:

`existing.check_in < new.check_out` та `existing.check_out > new.check_in`.

День виїзду одного гостя може бути днем заїзду іншого.

#### Розрахунок вартості

Вартість розраховується на backend на основі актуальної ціни `RentalUnit.price_per_night`.

`total_price = price_per_night * кількість ночей`

Значення `price_per_night` та `total_price` передаються клієнту тільки для читання. 
Frontend не може самостійно встановлювати вартість бронювання.

#### Захист від одночасного бронювання

Створення бронювання виконується в межах `transaction.atomic()`.

Для відповідного `RentalUnit` використовується `select_for_update()`, щоб запобігти одночасному 
створенню бронювань понад доступну кількість.

#### Успішна відповідь

- `201 Created` — бронювання успішно створено.
- Початковий статус — `PENDING`.

Відповідь містить:
- `id`;
- `user`;
- `rental_unit`;
- `property_id`;
- `property_title`;
- `rental_unit_title`;
- `check_in`;
- `check_out`;
- `guests`;
- `contact_name`;
- `contact_phone`;
- `contact_email`;
- `special_requests`;
- `price_per_night`;
- `total_price`;
- `status`;
- `created_at`;
- `updated_at`.

Дати повертаються у форматі `YYYY-MM-DD`, час створення та оновлення — у форматі ISO 8601.

#### Помилки

- `400 Bad Request` — відсутні обов'язкові поля або невалідні дані;
- `400 Bad Request` — неправильний формат ID типу розміщення;
- `400 Bad Request` — дата заїзду в минулому;
- `400 Bad Request` — дата виїзду не пізніше за дату заїзду;
- `400 Bad Request` — неправильна кількість гостей;
- `400 Bad Request` — перевищена місткість типу розміщення;
- `400 Bad Request` — немає доступних одиниць житла на вибраний період;
- `403 Forbidden` — користувач не має профілю або ролі `USER`;
- `404 Not Found` — опублікований тип розміщення не знайдено.

### 7.3. GET `/api/bookings/{id}/`

Повертає деталі конкретного бронювання.

**Доступ:** тільки власник бронювання (користувач, який його створив).

- `200 OK` — повна інформація про бронювання.
- `401 Unauthorized` — користувач не авторизований.
- `403 Forbidden` — спроба переглянути чуже бронювання.
- `404 Not Found` — бронювання не знайдено.

### 7.4. POST `/api/bookings/{id}/cancel/`

Скасувати можна бронювання зі статусами:

Після скасування статус змінюється на `CANCELLED`. Таке бронювання більше не займає доступність житла.

**Відповіді:**

## 8. Owner --- функції власника

    ID.

Власник визначається через `request.user`.

`Booking → RentalUnit → Property → owner`.

**Доступ:** тільки авторизований користувач із роллю `OWNER`.

**Відповіді:**
- `200 OK` — масив бронювань власника.

- `401 Unauthorized` — користувач не авторизований.
- `403 Forbidden` — недостатньо прав або відсутній профіль.



### 8.3. PATCH `/api/owner/bookings/{id}/`

Дозволяє власнику змінювати статус бронювання, яке належить одному з його об'єктів житла.

**Доступ:** тільки авторизований користувач із роллю `OWNER`.

#### Дозволені переходи статусів

| Поточний статус | Дозволений новий статус |
|---|---|
| `PENDING` | `CONFIRMED`, `REJECTED` |
| `CONFIRMED` | `CANCELLED`, `COMPLETED`, `NO_SHOW` |
| `REJECTED` | Немає |
| `CANCELLED` | Немає |
| `COMPLETED` | Немає |
| `NO_SHOW` | Немає |

Статуси `REJECTED`, `CANCELLED`, `COMPLETED` та `NO_SHOW` є кінцевими. 
Повторна активація такого бронювання не дозволяється.

#### Додаткові перевірки

- `COMPLETED` можна встановити у дату виїзду або пізніше.
- `NO_SHOW` можна встановити в день заїзду або пізніше.
- Власник може змінювати статуси тільки бронювань власних об'єктів житла.
- Після переходу в `REJECTED` або `CANCELLED` бронювання більше не займає доступність житла.

#### Приклад запиту

```json
{
    "status": "CONFIRMED"
}
```

#### Відповіді

- `200 OK` — статус успішно змінено.
- `400 Bad Request` — недозволений перехід між статусами.
- `400 Bad Request` — спроба встановити `COMPLETED` до дати виїзду.
- `400 Bad Request` — спроба встановити `NO_SHOW` раніше дати заїзду.
- `403 Forbidden` — користувач не має ролі `OWNER` або бронювання належить іншому власнику.
- `404 Not Found` — бронювання не знайдено.

Приклад помилки переходу:

```json
{
    "detail": "Invalid status transition.",
    "current_status": "REJECTED",
    "allowed_statuses": []
}
```

## 13. Загальні обмеження поточної реалізації

1. Backend використовує Django ORM та PostgreSQL для роботи з користувачами,
профілями, об'єктами житла (`Property`), типами розміщення (`RentalUnit`),
зручностями (`Amenity`), категоріями (`Category`), добірками (`PropertyCollection`)
та зображеннями (`PropertyImage`).

2. Моделі `Profile`, `Property`, `RentalUnit`, `Amenity`, `Category`,
`PropertyCollection`, `PropertyImage` та `Booking` створені,
а відповідні початкові міграції застосовані до бази даних.

3. Автентифікація реалізована на основі Django Authentication та JWT.
Реєстрація користувачів, вхід, оновлення токенів, вихід і отримання інформації
про поточного користувача працюють із реальною базою даних.

4.Основні операції з об'єктами житла, типами розміщення,
зручностями, категоріями, добірками та зображеннями реалізовані через Django ORM.

5. Для основних сценаріїв роботи з типами розміщення перевірено створення,
перегляд, редагування, деактивацію, автентифікацію, рольовий доступ та контроль
належності об'єкта власнику.


6. Операції з бронюваннями (`Booking`) реалізовані через Django ORM та реальну базу 
даних PostgreSQL. Mock-дані для створення, перегляду, скасування та зміни 
статусів бронювань не використовуються.

7. Адміністративні операції з користувачами (`Admin Users`), об'єктами житла 
(`Admin Properties`), категоріями (`Admin Categories`) та добірками (`Admin Collections`)
працюють із реальною базою даних PostgreSQL. Зміни, внесені через відповідні endpoint-и, 
зберігаються в базі даних.

8. Операції власника з перегляду та зміни бронювань реалізовані через Django ORM. Доступ до 
бронювань обмежується належністю об'єкта житла поточному авторизованому власнику.

9. Mock-дані для операцій із бронюваннями більше не використовуються. Дані бронювань 
 зберігаються в таблиці `Booking` та не втрачаються після перезапуску сервера.

10. Автоматизовані тести для застосунків `accounts`, `properties` та `bookings` наразі 
не реалізовані. Перевірка функціональності виконувалася вручну через API-запити, 
браузерну консоль та Django Shell. Для бронювань перевірено створення, доступність, 
перетин дат, зміну статусів, права доступу та конкурентні запити в PostgreSQL.

11. Налаштування безпеки та конфігурації середовища потребують додаткового доопрацювання
перед розгортанням у production-середовищі. Зокрема, необхідно налаштувати захищене
зберігання секретного ключа, параметри `DEBUG`, `ALLOWED_HOSTS` та конфігурацію
електронної пошти.

12. API-контракт описує поточну реалізацію backend. Після переведення mock-операцій
на Django ORM, внесення змін до бізнес-логіки та проведення повторного тестування
документація має бути актуалізована відповідно до фактичної поведінки endpoint-ів.
