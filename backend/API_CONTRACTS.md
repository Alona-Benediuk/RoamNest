# RoamNest API Contracts

## 1. Загальна інформація

**Base URL:** `http://127.0.0.1:8000`

**Джерело даних:** backend використовує Django ORM та PostgreSQL для роботи 
з користувачами, профілями, об'єктами житла, типами розміщення, зручностями та 
зображеннями. Операції з бронюваннями та адміністративні операції з 
користувачами й об'єктами житла наразі частково використовують mock-дані 
з `backend/mock_data.py`. Зміни в mock-структурах зберігаються лише в пам'яті
та не записуються до бази даних.

**Доступ та автентифікація:** Автентифікація, профіль, операції з об'єктами житла, 
типами розміщення, зручностями та зображеннями працюють із реальною базою даних. 
Операції з бронюваннями та частина адміністративних операцій наразі використовують 
mock-структури.

У прикладах `{id}` означає числовий ID ресурсу.

## 3. Authentication — автентифікація

- `POST /api/auth/register/` — реєстрація користувача.
- `POST /api/auth/login/` — перевірка облікових даних і отримання JWT.
- `POST /api/auth/refresh/` — оновлення access-токена.
- `POST /api/auth/logout/` — відкликання refresh-токена.
- `GET /api/auth/me/` — отримання даних поточного користувача за JWT.

Захищені endpoint-и потребують заголовка `Authorization: Bearer <access_token>`.

Типові відповіді:
- `401 Unauthorized` — відсутній або недійсний токен.
- `403 Forbidden` — користувач не має необхідних прав.

## 4. Properties --- житло

### 4.1. GET `/api/properties/`

Повертає список житла зі статусом `PUBLISHED`. Перед поверненням із
кожного об'єкта прибираються неопубліковані типи розміщення (`rental_units`).

#### Query-параметри

  ----------------------------------------------------------------------------
  Параметр                Тип                     Опис
  ----------------------- ----------------------- ----------------------------
  `city`                  string                  Пошук за входженням підрядка
                                                  в назву міста, без
                                                  урахування регістру

  `country`               string                  Пошук за входженням підрядка
                                                  в назву країни, без
                                                  урахування регістру

  `property_type`         string                  Точне порівняння типу житла
                                                  без урахування регістру

  `guests`                integer                 Залишає об'єкти, де є
                                                  опублікований тип розміщення
                                                  з `max_guests >= guests`

  `max_guests`            integer                 Залишає об'єкти, де є
                                                  опублікований тип розміщення
                                                  з `max_guests <= max_guests`

  `min_price`             number                  Мінімальна ціна за ніч,
                                                  включно з межею

  `max_price`             number                  Максимальна ціна за ніч,
                                                  включно з межею

  `amenities`             повторюваний integer    ID зручностей; об'єкт має
                                                  містити всі передані ID

  `ordering`              string                  `price` --- за зростанням
                                                  мінімальної ціни типу
                                                  розміщення; `-price` --- за
                                                  спаданням
  ----------------------------------------------------------------------------

Приклад:
`/api/properties/?city=Kyiv&guests=2&min_price=500&max_price=3000&amenities=1&amenities=2&ordering=price`


#### Відповіді

-   `200 OK` --- масив об'єктів.
-   `400 Bad Request`:
    -   `{"detail": "Invalid numeric filter parameter."}` --- некоректне
        числове значення, кількість гостей менша за 1 або від'ємна ціна;
    -   `{"detail": "min_price cannot exceed max_price."}` ---
        мінімальна ціна більша за максимальну;
    -   `{"detail": "amenities must contain integer IDs."}` --- ID
        зручності не є цілим числом;
    -   `{"detail": "Unsupported ordering parameter."}` ---
        непідтримуване значення `ordering`.

**Примітка:** сортування використовує мінімальну ціну серед
опублікованих типів розміщення. Якщо об'єкт не має жодного
опублікованого типу розміщення, сортування може спричинити помилку
сервера.

### 4.2. POST `/api/properties/`

Створює новий об'єкт житла зі статусом `NEW`, порожніми масивами
`amenities`, `rental_units` та `images`.

#### Обов'язкові поля

  Поле              Тип
  ----------------- --------
  `title`           string
  `description`     string
  `property_type`   string
  `address`         string
  `city`            string
  `country`         string

Власник об'єкта визначається автоматично за поточним автентифікованим користувачем. 
Передавати owner у тілі запиту не потрібно.

#### Відповіді

-   `201 Created` --- створений об'єкт.
-   `400 Bad Request`:
    -   `{"detail": "Required fields are missing.", "fields": [...]}`
        --- відсутні або порожні обов'язкові поля;

### 4.3. GET `/api/properties/{id}/`

Повертає деталі об'єкта лише тоді, коли його статус --- `PUBLISHED`.
Неопубліковані типи розміщення не включаються до `rental_units`.

-   `200 OK` --- об'єкт житла.
-   `404 Not Found` --- `{"detail": "Property not found."}`, якщо об'єкт
    відсутній або не опублікований.

### 4.4. PATCH `/api/properties/{id}/`

Дозволені поля:

-   `title`
-   `description`
-   `property_type`
-   `address`
-   `city`
-   `country`

Кожне передане поле має бути непорожнім рядком. Значення зберігається
після обрізання пробілів на початку та в кінці. Інші поля ігноруються.

-   `200 OK` --- оновлений об'єкт.
-   `400 Bad Request` ---
    `{"detail": "<field> must be a non-empty string."}`, якщо передане
    дозволене поле не є непорожнім рядком.
-   `404 Not Found` --- `{"detail": "Property not found."}`.

### 4.5. DELETE `/api/properties/{id}/`

Змінює статус об'єкта на `INACTIVE`; об'єкт не видаляється зі списку.

-   `200 OK`:

    ``` json
    {
      "detail": "Property deactivated successfully.",
      "id": 1,
      "status": "INACTIVE"
    }
    ```

-   `404 Not Found` --- `{"detail": "Property not found."}`.

### 4.6. GET `/api/amenities/`

Повертає записи з таблиці Amenity.

-   `200 OK`.

### 4.7. Rental Units — типи розміщення (кімнати)

API забезпечує перегляд, створення, редагування та
деактивацію типів розміщення, пов'язаних з об'єктами житла.

На відміну від частини endpoint-ів Properties, операції з 
RentalUnit використовують Django ORM та реальну базу даних.

#### 4.7.1. GET `/api/properties/{id}/rooms/`

Повертає список опублікованих кімнат конкретного об'єкта житла.

**Доступ:** Guest, USER, OWNER, ADMIN.

- `200 OK` — масив опублікованих кімнат.
- `404 Not Found` — об'єкт житла відсутній або не опублікований.

#### 4.7.2. POST `/api/properties/{id}/rooms/`

Створює новий тип розміщення для зазначеного об'єкта житла.

**Доступ:** лише автентифікований користувач
із роллю `OWNER`, якому належить об'єкт.

**Поля запиту:**

| Поле | Тип | Опис |
|---|---|---|
| `title` | string | Назва кімнати |
| `description` | string | Опис |
| `room_type` | string | Тип розміщення |
| `price_per_night` | decimal | Ціна за ніч |
| `max_guests` | integer | Максимальна кількість гостей |
| `bedrooms` | integer | Кількість спалень |
| `beds` | integer | Кількість ліжок |
| `bathrooms` | integer | Кількість ванних кімнат |
| `rooms_count` | integer | Кількість доступних кімнат |
| `amenities` | array of integers | ID зручностей |
| `is_published` | boolean | Статус публікації |

**Відповіді:**

- `201 Created` — кімнату створено.
- `400 Bad Request` — некоректні або невалідні дані.
- `401 Unauthorized` — відсутній або недійсний токен.
- `403 Forbidden` — користувач не має ролі OWNER або не володіє об'єктом.
- `404 Not Found` — об'єкт житла не знайдений.

#### 4.7.3. GET `/api/properties/rooms/{id}/`

Повертає детальну інформацію про опубліковану кімнату.

**Доступ:** Guest, USER, OWNER, ADMIN.

- `200 OK` — інформація про кімнату.
- `404 Not Found` — кімната відсутня, не опублікована 
або її об'єкт житла не опублікований.

#### 4.7.4. PATCH `/api/properties/rooms/{id}/`

Оновлює дані кімнати.

**Доступ:** лише автентифікований власник (`OWNER`), якому належить об'єкт житла.

Дозволяється часткове оновлення полів кімнати.

- `200 OK` — оновлена інформація про кімнату.
- `400 Bad Request` — невалідні дані.
- `401 Unauthorized` — відсутній або недійсний токен.
- `403 Forbidden` — користувач не має ролі OWNER або 
намагається змінити кімнату іншого власника.
- `404 Not Found` — кімната не знайдена.

#### 4.7.5. DELETE `/api/properties/rooms/{id}/`

Деактивує кімнату шляхом встановлення `is_published = false`.

Фізичне видалення запису з бази даних не виконується.

**Доступ:** лише автентифікований власник (`OWNER`), якому належить об'єкт житла.

**Відповіді:**

- `200 OK` — успішна деактивація:

```json
{
  "detail": "Room deactivated successfully.",
  "id": 4,
  "is_published": false
}
```

- `401 Unauthorized` — відсутній або недійсний токен.
- `403 Forbidden` — недостатньо прав доступу.
- `404 Not Found` — кімната не знайдена.

Після деактивації кімната не повертається в публічному списку 
та недоступна через публічний endpoint отримання деталей.

#### Перевірка прав доступу

Під час тестування перевірено такі сценарії:

| Сценарій | HTTP-статус |
|---|---:|
| OWNER створює кімнату | 201 |
| OWNER переглядає кімнату | 200 |
| OWNER редагує власну кімнату | 200 |
| OWNER деактивує власну кімнату | 200 |
| Guest переглядає опубліковані кімнати | 200 |
| Guest отримує деактивовану кімнату | 404 |
| USER намагається створити кімнату | 403 |
| USER намагається редагувати кімнату | 403 |
| USER намагається деактивувати кімнату | 403 |
| OWNER намагається редагувати чужу кімнату | 403 |

Таким чином, перевірено базові CRUD-операції, автентифікацію, 
рольовий доступ та контроль належності кімнати власнику об'єкта.

## 5. Property Images --- зображення житла

Зображення зберігається в таблиці PropertyImage.
rental_unit необов'язковий, якщо він переданий, перевіряється його 
належність до відповідного об'єкта житла.
Додавання та видалення зображень працюють через ORM.
Операції доступні власнику відповідного об'єкта.

### 5.1. POST `/api/properties/{id}/images/`

#### Поля запиту

  -----------------------------------------------------------------------
  Поле              Тип               Обов'язкове       Опис
  ----------------- ----------------- ----------------- -----------------
  `image_url`       string            Так               URL зображення;
                                                        має бути
                                                        непорожнім

  `is_main`         boolean           Ні                Чи є зображення
                                                        головним; за
                                                        замовчуванням
                                                        `false`

  `rental_unit`    integer            Ні                ID типу розміщення,
                                                        необов'язкове поле.
  -----------------------------------------------------------------------

Якщо зображення перше, воно автоматично стає головним. Якщо передано
`is_main: true`, попередні зображення цього об'єкта перестають бути
головними.


-   `201 Created` --- створене зображення з полями `id`, `image_url`,
    `is_main`, `rental_unit`.
-   `400 Bad Request`:
    -   `{"detail": "image_url is required."}`;
    -   `{"detail": "is_main must be a boolean."}`.
-   `404 Not Found` --- `{"detail": "Property not found."}`.

### 5.2. DELETE `/api/properties/{id}/images/{image_id}/`

Запис видаляється з таблиці PropertyImage

-   `204 No Content` --- успішне видалення без тіла відповіді.
-   `404 Not Found`:
    -   `{"detail": "Property not found."}`;
    -   `{"detail": "Image not found."}`.

## 7. Bookings --- бронювання

### 7.1. GET `/api/bookings/`

Повертає список бронювань поточного автентифікованого користувача. 
Користувач визначається за JWT (request.user), передавати user_id не потрібно.

### 7.2. POST `/api/bookings/`

#### Обов'язкові поля

  -----------------------------------------------------------------------
  Поле                    Тип                     Опис
  ----------------------- ----------------------- -----------------------
  `room`                  integer або значення,   ID типу розміщення
                          яке можна перетворити   
                          на integer              

  `check_in`              string `YYYY-MM-DD`     Дата заїзду

  `check_out`             string `YYYY-MM-DD`     Дата виїзду

  `guests`                integer або значення,   Кількість гостей
                          яке можна перетворити   
                          на integer              

  `contact_name`          непорожнє значення      Ім'я контактної особи

  `contact_phone`         непорожнє значення      Телефон

  `contact_email`         непорожнє значення      Email
  -----------------------------------------------------------------------

Додаткові поля:

-   `user` --- ID користувача, за замовчуванням `1`. Користувач має
    існувати в `MOCK_USERS` і мати роль `USER`.
-   `special_requests` --- рядок побажань, за замовчуванням `""`.

#### Перевірки

-   Заїзд не може бути в минулому.
-   Виїзд має бути пізніше за заїзд.
-   Кількість гостей має бути не меншою за 1 та не перевищувати
    `max_guests` типу розміщення.
-   Тип розміщення має існувати, бути опублікованим, а його об'єкт житла
    --- мати статус `PUBLISHED`.
-   Для доступності рахується кількість бронювань цього типу розміщення
    зі статусами `PENDING` або `CONFIRMED`, які перетинаються з обраним
    періодом. Запит відхиляється, якщо кількість таких бронювань
    дорівнює або перевищує `rooms_count` (за замовчуванням `1`).

#### Успішна відповідь

-   `201 Created` --- створене бронювання. Воно містить `id`, `user`,
    `room`, `property_id`, `property_title`, `room_title`, `check_in`,
    `check_out`, `guests`, `contact_name`, `contact_phone`,
    `contact_email`, `special_requests`, `price_per_night`,
    `total_price`, `status`, `created_at`, `updated_at`.
-   Початковий статус --- `PENDING`.
-   `total_price` обчислюється як ціна за ніч, помножена на кількість
    ночей, і повертається рядком із двома знаками після коми.
-   `created_at` та `updated_at` мають значення `null`.

#### Помилки

-   `400 Bad Request`:
    -   `{"detail": "Required fields are missing.", "fields": [...]}`;
    -   `{"detail": "Invalid room, guests, or date format."}`;
    -   `{"detail": "Check-in cannot be in the past."}`;
    -   `{"detail": "Check-out must be after check-in."}`;
    -   `{"detail": "Guests must be at least 1."}`;
    -   `{"detail": "Too many guests for this room."}`;
    -   `{"detail": "User ID must be an integer."}`;
    -   `{"detail": "Guest user not found."}`;
    -   `{"detail": "No rooms available for these dates."}`.
-   `404 Not Found` --- `{"detail": "Published room not found."}`.

### 7.3. GET `/api/bookings/{id}/`

-   `200 OK` --- повний об'єкт бронювання.
-   `404 Not Found` --- `{"detail": "Booking not found."}`.

### 7.4. POST `/api/bookings/{id}/cancel/`

Змінює статус бронювання на `CANCELLED`.

-   `200 OK` --- оновлений об'єкт бронювання.
-   `400 Bad Request` --- `{"detail": "Booking is already cancelled."}`.
-   `404 Not Found` --- `{"detail": "Booking not found."}`.

## 8. Owner --- функції власника

### 8.1. GET `/api/owner/properties/`

-   `200 OK` --- масив об'єктів, у яких `owner` відповідає переданому
    ID.
-   Якщо збігів немає, повертається порожній масив.

### 8.2. GET `/api/owner/bookings/`

Повертає бронювання, пов'язані з об'єктами житла поточного авторизованого
користувача з роллю OWNER. Власник визначається через request.user.

Повертає бронювання, `property_id` яких належить об'єктам з відповідним
`owner`.

-   `200 OK` --- масив бронювань.
-   Якщо збігів немає, повертається порожній масив.

### 8.3. PATCH `/api/owner/bookings/{id}/`

Тіло запиту:

``` json
{
  "status": "CONFIRMED"
}
```

Дозволені статуси: `PENDING`, `CONFIRMED`, `CANCELLED`.

-   `200 OK` --- оновлений об'єкт бронювання.

-   `400 Bad Request`:

    ``` json
    {
      "detail": "Invalid booking status.",
      "allowed_statuses": ["CANCELLED", "CONFIRMED", "PENDING"]
    }
    ```

-   `404 Not Found` --- `{"detail": "Booking not found."}`.

### 10.1. GET `/api/admin/properties/`

-   `204 No Content` --- об'єкт видалено, тіло відповіді відсутнє.
-   `404 Not Found` --- `{"error": "Property not found."}`.

## 11. Загальні обмеження поточної реалізації

1. Backend використовує Django ORM та PostgreSQL для роботи з користувачами, 
профілями, об'єктами житла (`Property`), типами розміщення (`RentalUnit`), 
зручностями (`Amenity`) та зображеннями (`PropertyImage`).

2. Моделі `Profile`, `Property`, `RentalUnit`, `Amenity`, `PropertyImage` та `Booking`
створені, а відповідні початкові міграції застосовані до бази даних.

3. Автентифікація реалізована на основі Django Authentication та JWT. 
Реєстрація користувачів, вхід, оновлення токенів, вихід і отримання інформації 
про поточного користувача працюють із реальною базою даних.

4. Основні операції з об'єктами житла, типами розміщення, зручностями та 
зображеннями реалізовані через Django ORM.

5. Для основних сценаріїв роботи з типами розміщення перевірено створення, 
перегляд, редагування, деактивацію, автентифікацію, рольовий доступ та контроль 
належності об'єкта власнику.

6. Операції з бронюваннями (`Booking`) наразі використовують mock-структури 
з `backend/mock_data.py`. Модель `Booking` та серіалізатор `BookingSerializer` 
уже створені, проте поточні API-представлення ще не переведені на роботу з базою даних.

7. Адміністративні операції з користувачами та об'єктами житла 
(`Admin Users`, `Admin Properties`) також використовують mock-дані. 
Зміни, внесені через відповідні endpoint-и, не зберігаються в PostgreSQL.

8. Операції власника з перегляду його об'єктів житла використовують Django ORM, 
тоді як операції перегляду та зміни бронювань власника наразі працюють із mock-даними.

9. Mock-дані зберігаються в оперативній пам'яті застосунку. Зміни, внесені до них 
під час роботи сервера, не є постійними та втрачаються після його перезапуску.

10. Автоматизовані тести для застосунків `accounts`, `properties` та `bookings` наразі 
не реалізовані. Перевірка окремих сценаріїв виконувалася вручну через API-запити.

11. Налаштування безпеки та конфігурації середовища потребують додаткового доопрацювання 
перед розгортанням у production-середовищі. Зокрема, необхідно налаштувати захищене 
зберігання секретного ключа, параметри `DEBUG`, `ALLOWED_HOSTS` та конфігурацію 
електронної пошти.

12. API-контракт описує поточну реалізацію backend. Після переведення mock-операцій 
на Django ORM, внесення змін до бізнес-логіки та проведення повторного тестування 
документація має бути актуалізована відповідно до фактичної поведінки endpoint-ів.
